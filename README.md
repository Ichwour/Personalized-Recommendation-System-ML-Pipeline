# Personalized-Recommendation-System-ML-Pipeline
Built a personalized recommendation system for product recommendation using a two-stage architecture: candidate generation followed by learning-to-rank.
The candidate generation stage first reduces the catalog from approximately **5,500 products** to **1,000 candidates**, preserving around **90% recall**.  
A refined retrieval layer then compresses this candidate pool to **100 candidates**, preserving around **53% recall** while maintaining product-signature diversity.
The final candidate set is passed to a **CatBoost ranking model**, which reorders the retrieved products for each user.  
In offline evaluation, the full pipeline achieved approximately **29% Hit@10**, with strong personalization and low overlap between different users' recommendation lists.

## Candidate-Level Feature Analysis

To understand which features separate true purchases from baseline candidates, I analyzed the candidate-level dataset generated from the baseline retrieval space.

Each event contained:
- 1 true purchased item (`label = 1`)
- 999 baseline candidate negatives (`label = 0`)

Total dataset size:
- Events: **6,643**
- Rows: **6,643,000**
- Positives: **6,643**
- Negatives: **6,636,357**

The analysis was performed using:
- **Chi-square test** for categorical product attributes
- **Kolmogorov–Smirnov test** for numeric feature distributions
- **Pearson correlation** for numeric feature association with the target label

```python
from scipy.stats import chi2_contingency, ks_2samp, pearsonr

contingency = pd.crosstab(df["vendor"], df["label"])

negative_price = df[df["label"] == 0]["price"].dropna()

```

### Results

The strongest numeric separation was observed in **price**:
- True item mean price: **32.56**
- Candidate mean price: **68.15**
- True item median price: **18.00**
- Candidate median price: **30.00**
- KS statistic: **0.238**

This indicates that true purchases were generally shifted toward lower-priced items compared to the baseline candidate pool.

The second useful numeric signal was **profile_score**:
- True item mean profile_score: **0.347**
- Candidate mean profile_score: **0.283**
- KS statistic: **0.151**
- Pearson correlation: **0.0135**

The Pearson correlation was weak due to the highly imbalanced structure of the dataset (1 positive vs 999 negatives per event), but the distribution shift confirmed that profile similarity still carried useful signal.

Categorical features also showed statistically significant separation, but with weak effect size:
- `vendor`: Cramer's V ≈ **0.035**
- `varietals_1`: Cramer's V ≈ **0.029**
- `varietals_2`: Cramer's V ≈ **0.028**
- `region`: Cramer's V ≈ **0.025**
- `country`: Cramer's V ≈ **0.011**
- `color`: Cramer's V ≈ **0.006**
- `sugar`: Cramer's V ≈ **0.005**

These results suggest that product metadata contains signal, but no single categorical feature strongly separates true purchases from candidate alternatives.

### Key Problem: Weak Separation in the Candidate Space

The analysis showed that the features did contain useful signal, but mostly at a broad separation level.
Price, profile score, vendor, varietals, region, and other metadata helped distinguish true purchases from the overall candidate pool. However, these signals were not strong enough on their own to reliably separate the true item from the closest competing candidates.
This was expected because the candidate pool was already generated by a baseline recommender. The negatives were not random catalog items; they were plausible alternatives that had already passed an initial relevance filter.
As a result, the task became a hard-negative ranking problem:
- the features could separate obviously weaker candidates
- the remaining candidates were already relatively relevant
- true purchases and strong negatives often looked similar
- deeper ranking required combining many weak-to-moderate signals rather than relying on one dominant feature

### Sequential Purchase Pattern Analysis

After the candidate-level feature analysis showed that static features provided useful but limited separation, I explored whether user behavior contained a stronger **sequential structure**.
Instead of analyzing purchases as isolated events, I studied transitions between consecutive purchases for each user.  
The goal was to understand whether the next purchase tends to follow repeatable behavioral patterns rather than being explained only by static product relevance.
For this analysis, each purchased item was mapped into a **profile-similarity bucket** based on its `profile_score`.
The `profile_score` represents how well an item matches the user's historical preferences, with more recent behavior having stronger influence through memory decay.
Rather than treating `profile_score` only as a static relevance feature, I also used it as a behavioral state.  
This allowed me to analyze how users move between different similarity zones over time and use these transition patterns later in the retrieval stage.

### Method

For every user, purchases were ordered chronologically.  
Each purchased item was assigned to a `profile_score` bucket, and transitions were calculated from the current purchase bucket to the next purchase bucket.
This produced a transition matrix showing how often users moved from one profile-similarity zone to another.

```python
import pandas as pd

def assign_profile_bucket(score: float) -> str:
    if score < 0.20:
        return "0.00-0.20"
    elif score < 0.45:
        return "0.20-0.45"
    elif score < 0.70:
        return "0.45-0.70"
    elif score < 0.90:
        return "0.70-0.90"
    else:
        return "0.90-1.00"


df = df.sort_values(["client_id", "event_time"])

df["profile_bucket"] = df["profile_score"].apply(assign_profile_bucket)

df["next_profile_bucket"] = (
    df.groupby("client_id")["profile_bucket"]
      .shift(-1)
)

valid_transitions = df.dropna(subset=["next_profile_bucket"])

transition_counts = (
    valid_transitions
    .groupby(["profile_bucket", "next_profile_bucket"])
    .size()
    .reset_index(name="transition_count")
)

transition_matrix = (
    transition_counts
    .pivot_table(
        index="profile_bucket",
        columns="next_profile_bucket",
        values="transition_count",
        fill_value=0
    )
)

transition_matrix_pct = transition_matrix.div(
    transition_matrix.sum(axis=1),
    axis=0
)
```

### Approximate Findings

The transition matrix showed that user movement across profile-similarity buckets had a clear repeated structure rather than being evenly distributed across possible next states.
Several strong transition patterns appeared:

| Current profile-score bucket | Most common next movement | Observed probability | Baseline probability | Interpretation |
|---|---|---:|---:|---|
| `0.00-0.20` | Toward `0.80+` | ~46% | ~32% | After a low-similarity purchase, users often returned to items with a much stronger profile match |
| `0.80+` | Toward approximately `0.30-0.45` | ~54% | ~32% | After a very profile-aligned purchase, users often shifted back toward a more moderate similarity range |
| `0.25-0.45` | Stayed in `0.25-0.45` | ~82% | ~32% | Moderate-similarity behavior was highly stable and often repeated in the next purchase |

The baseline probability represents a simple probabilistic benchmark for predicting the next profile-score zone.
These results showed that customers do not always move monotonically toward higher profile similarity.  
Instead, the next purchase often depends on the user's previous similarity state.
The main takeaway was that `profile_score` should not be treated as a simple "higher is always better" ranking signal.

## Refined Top-100 Retrieval from the Popularity Baseline

The retrieval stage started with a simple but strong popularity-based baseline.
The goal of the baseline was to create a broad candidate pool with high recall before applying more personalized filtering.  
At this stage, the system did not try to produce the final recommendation order. Its purpose was to make sure that the true purchased item was likely to remain inside the candidate space.

### Popularity Baseline: Top-1000 Candidate Pool

For each recommendation event, product popularity was calculated causally using only purchases that happened before the current event timestamp.
The baseline used several historical popularity windows:
- `pop_365d`: long-term stable demand
- `pop_60d`: medium-term demand
- `pop_30d`: recent demand and short-term trend

Each product received popularity features based on how often it appeared in the corresponding historical window.

```python
import pandas as pd

def calculate_window_popularity(
    events: pd.DataFrame,
    current_time: pd.Timestamp,
    window_days: int
) -> pd.DataFrame:
    window_start = current_time - pd.Timedelta(days=window_days)

    history = events[
        (events["event_time"] < current_time) &
        (events["event_time"] >= window_start)
    ]

    popularity = (
        history.groupby("product_id")
               .size()
               .reset_index(name=f"pop_{window_days}d")
    )

    return popularity

The three popularity windows were then combined into a single baseline score.

def minmax_normalize(series: pd.Series) -> pd.Series:
    if series.max() == series.min():
        return pd.Series(0.0, index=series.index)

    return (series - series.min()) / (series.max() - series.min())


candidates["pop_365_norm"] = minmax_normalize(candidates["pop_365d"])
candidates["pop_60_norm"] = minmax_normalize(candidates["pop_60d"])
candidates["pop_30_norm"] = minmax_normalize(candidates["pop_30d"])

candidates["baseline_score"] = (
    W_LONG_TERM * candidates["pop_365_norm"] +
    W_MEDIUM_TERM * candidates["pop_60_norm"] +
    W_SHORT_TERM * candidates["pop_30_norm"]
)

The baseline candidates were selected by sorting products by this combined popularity score:
top_1000_candidates = (
    candidates.sort_values("baseline_score", ascending=False)
              .head(1000)
)
```
This baseline reduced the full catalog from approximately 5,500 products to 1,000 candidates, while preserving 90% recall.
This result showed that popularity was a strong retrieval signal in this dataset.
However, the top-1000 candidate pool was still too large and too generic to be used directly as the final recommendation set.

### Profile-Aware Refinement

The next step was to compress the baseline top-1000 into a stronger top-100 retrieval set.
This refinement still started from the popularity baseline, but added a profile-score filter.
The profile_score represented how well a candidate matched the user's historical preferences.
It was calculated causally using only the user's previous behavior before the current event, with memory decay applied so that recent purchases had stronger influence than older ones.
The sequential transition analysis showed that the next purchase was not always expected to have the highest possible profile_score.
Instead, users often moved between profile-score zones in repeated patterns.
Because of this, the refinement did not apply a hard filter such as:
keep only candidates with the highest profile_score
Instead, it applied a smoothed filter around the expected next profile-score zone.

```python
import numpy as np

def smooth_profile_filter(
    candidate_profile_score: float,
    expected_profile_center: float,
    sigma: float
) -> float:
    """
    Gives higher weight to candidates closer to the expected next
    profile-score zone, while still keeping weaker matches available.
    """
    distance = candidate_profile_score - expected_profile_center

    return np.exp(-(distance ** 2) / (2 * sigma ** 2))


top_1000_candidates["profile_filter_score"] = (
    top_1000_candidates["profile_score"].apply(
        lambda score: smooth_profile_filter(
            candidate_profile_score=score,
            expected_profile_center=expected_next_profile_center,
            sigma=PROFILE_SMOOTHING_WIDTH
        )
    )
)
top_1000_candidates["refined_score"] = (
    W_BASELINE * top_1000_candidates["baseline_score"] +
    W_PROFILE_FILTER * top_1000_candidates["profile_filter_score"]
)
```

The profile filter was intentionally soft.
Candidates outside the expected zone were penalized, but not completely removed. This preserved recall and allowed the final top-100 set to keep enough alternative products for the ranking stage.

### Diversity-Aware Reordering and Selection

After refined scoring, the system applied a diversity-aware reordering step.
The purpose was to avoid a top-100 candidate set filled with many near-identical products.
In this dataset, many products could share very similar metadata, such as the same country, region, color, sugar level, varietal, or vendor.
To control this, each product was mapped into a candidate signature:

```python
signature_columns = [
    "country",
    "region",
    "color",
    "sugar",
    "varietals_1",
    "vendor"
]

top_1000_candidates["signature"] = (
    top_1000_candidates[signature_columns]
    .fillna("unknown")
    .astype(str)
    .agg("|".join, axis=1)
)
```
The final top-100 was selected from the refined top-1000 using a diversity-aware procedure.
The selection first preferred high-scoring candidates, but limited repeated signatures.
If the initial high-scoring candidates were too concentrated in the same product signatures, the algorithm diluted the set by adding relevant lower-ranked candidates from underrepresented signatures.

```python
def select_diverse_top_k(
    candidates: pd.DataFrame,
    top_k: int = 100,
    max_per_signature: int = 2
) -> pd.DataFrame:
    candidates = candidates.sort_values("refined_score", ascending=False)

    selected = []
    selected_ids = set()
    signature_counts = {}

    for _, row in candidates.iterrows():
        signature = row["signature"]
        current_count = signature_counts.get(signature, 0)

        if current_count >= max_per_signature:
            continue

        selected.append(row)
        selected_ids.add(row["product_id"])
        signature_counts[signature] = current_count + 1

        if len(selected) >= top_k:
            break

    if len(selected) < top_k:
        remaining = candidates[~candidates["product_id"].isin(selected_ids)]

        for _, row in remaining.iterrows():
            selected.append(row)

            if len(selected) >= top_k:
                break

    return pd.DataFrame(selected)


top_100_candidates = select_diverse_top_k(
    candidates=top_1000_candidates,
    top_k=100,
    max_per_signature=MAX_PER_SIGNATURE
)
```

### Retrieval Result

The refined retrieval process worked as follows:
Full catalog:              ~5,500 products
Popularity baseline:       top-1,000 candidates, ~90% recall
Refined retrieval:         top-100 candidates,  ~53% recall

The final top-100 retrieval set was built from three ideas:
strong popularity-based baseline retrieval
soft profile-score filtering based on sequential behavior
diversity-aware reordering across product signatures
This produced a compact candidate set that preserved a large share of true future purchases while avoiding excessive concentration around a few dominant product types.

## Ranker Feature Generation

After the refined top-100 retrieval stage, the next step was to generate candidate-level features for the learn ranking model.
For each recommendation event, the system used the previously described retrieval pipeline:
Full catalog → popularity baseline top-1000 → profile-aware refinement → diverse top-100 candidates
The resulting top-100 candidates were then converted into a training dataset for the CatBoost ranker.
Each event formed one ranking group, where:
the true purchased item was marked as the positive candidate
the remaining retrieved products were treated as candidate negatives
all features were calculated using only information available before the event timestamp
The final training dataset was saved as a Parquet file to preserve the candidate-level structure efficiently.

### Tokenized Time-Decayed Profile Features

A major part of the ranker feature set was based on tokenized product attributes.
Each product was represented as a set of interpretable tokens, such as:
country:France
region:Champagne
color:White
sugar:Brut
varietal:Chardonnay
vendor:example_vendor
price_bin:medium

For every user and event, the system built a historical preference profile from previous purchases only.
Older interactions were down-weighted with time decay, while recent purchases had stronger influence.

```python
import numpy as np
import pandas as pd

def time_decay(days_since_event: float, half_life: float) -> float:
    return np.exp(-np.log(2) * days_since_event / half_life)

def build_user_token_profile(
    user_history: pd.DataFrame,
    current_time: pd.Timestamp,
    half_life: float
) -> dict:
    history = user_history[user_history["event_time"] < current_time].copy()

    history["days_since_event"] = (
        current_time - history["event_time"]
    ).dt.days

    history["decay_weight"] = history["days_since_event"].apply(
        lambda x: time_decay(x, half_life=half_life)
    )

    token_profile = {}

    for _, row in history.iterrows():
        for token in row["item_tokens"]:
            token_profile[token] = token_profile.get(token, 0.0) + row["decay_weight"]

    return token_profile
```

Each candidate item was then compared against the user's decayed token profile.

```python
def calculate_token_match_score(candidate_tokens: list[str], token_profile: dict) -> float:
    if not candidate_tokens:
        return 0.0

    return sum(token_profile.get(token, 0.0) for token in candidate_tokens) / len(candidate_tokens)


candidates["token_profile_match"] = candidates["item_tokens"].apply(
    lambda tokens: calculate_token_match_score(tokens, user_token_profile)
)
```

These features allowed the ranker to measure how well each candidate matched the user's historical preferences across product metadata, not only by a single profile score.

### Profile-Score Zone Features

In addition to direct token-profile matching, the ranker used features based on the user's tendency to move toward specific profile_score zones.
The earlier sequential analysis showed that users did not always move toward the highest possible profile similarity.
Depending on the previous behavioral state, the next purchase could be more likely to fall into a moderate, high, or exploratory profile-score zone.
For each event, the system estimated the user's expected next profile-score zone from historical transition patterns.
Then, each candidate received features describing how well it matched that expected zone.

```python
def distance_to_expected_zone(
    candidate_profile_score: float,
    expected_zone_center: float
) -> float:
    return abs(candidate_profile_score - expected_zone_center)
candidates["profile_zone_distance"] = candidates["profile_score"].apply(
    lambda score: distance_to_expected_zone(
        candidate_profile_score=score,
        expected_zone_center=expected_profile_zone_center
    )
)
candidates["profile_zone_match"] = 1.0 / (
    1.0 + candidates["profile_zone_distance"]
)
```

### Causality and Leakage Protection

Feature generation was built with strict causal validation.
For every event:
- popularity features used only purchases before the event timestamp
- user profile features used only the user's previous purchases
- token affinities were calculated only from past behavior
- profile-score zone features were derived from historical transition logic
- the true purchased item was not used to generate its own features
- candidate generation was performed before labeling candidates for training
- positive-item frequency was controlled so that repeated appearances of the same product as a positive label could not dominate training; products with unusually high positive frequency were limited relative to the average positive frequency of other items
This was important because recommendation datasets are highly vulnerable to leakage and popularity overfitting.  
Even small timestamp mistakes or uncontrolled repeated positives can make the model look stronger offline while failing in production-like evaluation.

## CatBoost Training

After the candidate-level feature dataset was generated, the final ranking stage was trained with CatBoost.
The model was trained as a ranking problem rather than a binary classification problem.  
Each recommendation event was treated as one ranking group:

one event_id / group_id = one ranking group
100 retrieved candidates = items inside the group
true purchased item = positive label
other retrieved candidates = negative labels

```python
from catboost import CatBoostRanker, Pool

feature_cols = [
    col for col in ranker_dataset.columns
    if col not in [
        "label",
        "group_id",
        "event_time",
        "client_id",
        "product_id"
    ]
]

ranker_dataset = ranker_dataset.sort_values("event_time")
train_df = ranker_dataset[ranker_dataset["event_time"] < VALIDATION_START].copy()
valid_df = ranker_dataset[ranker_dataset["event_time"] >= VALIDATION_START].copy()
train_pool = Pool(
    data=train_df[feature_cols],
    label=train_df["label"],
    group_id=train_df["group_id"],
    cat_features=cat_feature_cols
)
valid_pool = Pool(
    data=valid_df[feature_cols],
    label=valid_df["label"],
    group_id=valid_df["group_id"],
    cat_features=cat_feature_cols
)

model = CatBoostRanker(
    loss_function="YetiRank",
    eval_metric="NDCG:top=10",
    iterations=N_ITERATIONS,
    learning_rate=LEARNING_RATE,
    depth=DEPTH,
    random_seed=42,
    verbose=100
)

model.fit(
    train_pool,
    eval_set=valid_pool,
    use_best_model=True

```

The model was evaluated with ranking metrics rather than only classification metrics.
The main validation metrics were:
Hit@10: whether the true purchased item appeared in the top-10 ranked candidates
Hit@K: ranking quality across several cutoffs
MRR: how high the true item appeared on average
NDCG@10: rank-sensitive quality metric that rewards placing the positive item closer to the top

```python
import numpy as np
import pandas as pd

valid_df["prediction"] = model.predict(valid_pool)
valid_ranked = valid_df.sort_values(
    ["group_id", "prediction"],
    ascending=[True, False]
)
valid_ranked["rank"] = (
    valid_ranked.groupby("group_id")
                .cumcount() + 1
)

def hit_at_k(df: pd.DataFrame, k: int) -> float:
    top_k = df[df["rank"] <= k]
    hits = (
        top_k.groupby("group_id")["label"]
             .max()
    )

    return hits.mean()

def mrr(df: pd.DataFrame) -> float:
    positives = df[df["label"] == 1].copy()
    positives["reciprocal_rank"] = 1.0 / positives["rank"]
    return positives["reciprocal_rank"].mean()

validation_metrics = {
    "hit_at_1": hit_at_k(valid_ranked, 1),
    "hit_at_5": hit_at_k(valid_ranked, 5),
    "hit_at_10": hit_at_k(valid_ranked, 10),
    "hit_at_20": hit_at_k(valid_ranked, 20),
    "mrr": mrr(valid_ranked)
}
```

### Validation Result

Offline validation was designed as a simulation of real recommendation cases.
The dataset was split chronologically: the model was trained on earlier events and validated on future events that happened after the training period.  
This avoided random row-level splitting, which would be unsafe for recommendation systems because it can leak future popularity, user behavior, and product-demand patterns into training.
The validation process followed the same structure as a real recommendation request:

On offline validation, the full pipeline achieved approximately:
Retrieval recall@100:   ~60%
Final ranking Hit@10:   ~29%

This means that the retrieval stage first preserved the true item inside the top-100 candidate set in around 60% of evaluated events.
Then, the CatBoost ranker reordered those candidates and placed the true item inside the top-10 in approximately 29% of evaluated events.
This result was meaningful because the ranker was not choosing from the full catalog directly.
It was solving a hard ranking problem inside a compact candidate set where many negatives were already plausible alternatives.

## Conclusion and Applied Skills

This project resulted in a complete personalized recommendation pipeline built around a two-stage architecture:
candidate generation → refined retrieval → learning-to-rank

The system first reduced the product catalog from approximately 5,500 products to 1,000 candidates using a popularity-based baseline, preserving around 90% recall.
Then, a refined retrieval layer compressed the candidate set from 1,000 to 100 products, preserving around 53% recall while applying profile-aware filtering and diversity-aware candidate selection.
The final top-100 candidate set was passed to a CatBoost learning-to-rank model, which reordered candidates inside each recommendation event.

In offline future-event simulation, the final system achieved:
Non-personalized baseline Hit@10:    ~8.5%
Personalized system Hit@10:          ~29%
Retrieval recall@100:                ~60%

This result was substantially stronger than the non-personalized baseline.
The baseline could recommend generally popular products, but it did not adapt well to individual users.
The final system combined popularity, profile similarity, sequential behavior, product metadata, and ranking features to produce a stronger and more personalized top-10 recommendation list.
